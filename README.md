# U-Smile: Cardiac Patient Data Cleaning and Feature Selection

Reproducible data cleaning pipeline for the **U-Smile** project. The project includes a reproducible cleaning pipeline and baseline feature selection for recorded death.

---

### Folder Roles

* **`data/raw/`**: Contains the original, unaltered data files (`.csv` and `.xlsx`). Treat this folder as read-only.
* **`data/processed/`**: Stores cleaned, standardized output produced by `src/clean_data.py`.
* **`notebooks/`**: For inspecting data, testing snippets, and prototyping cleaning functions.
* **`src/clean_data.py`**: Orchestrates loading, the ordered cleaning steps in `clean_data(df)`, and saving. Keep transformation logic in the step modules.
* **`src/cleaning_steps/`**: Contains the cleaning functions. Keep similar tasks in the same file. Add new files when needed.

## Running the Pipeline

To run the entire data cleaning pipeline from the command line:

```bash
python src/clean_data.py

```

### What happens when you run it:

1. Loads raw data from `data/raw/cardiac_patient_data.csv` (or `.xlsx`).
2. Runs the cleaning functions imported from `cleaning_steps/` in the explicit order defined by `clean_data()`.
3. Exports the clean dataset to `data/processed/cardiac_patient_data_clean.csv`.

## Missing-Value Imputation

`clean_missing_values()` runs after column pruning and conversion of dates to
day counts. This lets it fill missing day counts as well as other supported
columns. It uses MissForest-style imputation: it repeatedly trains
random forests on known values to predict missing ones. Existing values stay
unchanged. Numeric columns use regression; text, categories, booleans and binary
numeric columns use classification.

Change `max_iter`, `n_estimators`, and `random_state` in
`src/cleaning_steps/missing_values.py` to control runtime and repeatability.
Pass numeric category-code columns in `categorical_columns` and columns to
leave out in `exclude_columns` (by default, `cid` and `cid.1`). If pruning removes
a column listed in `categorical_columns`, the function warns and continues
without it. It does not recreate pruned columns.

Dates, entirely empty columns, columns containing infinity, and unsupported
values stay unchanged. Mostly numeric text, such as `ALDOpg/ml`, must be cleaned
and converted to numbers first. The function warns when missing values remain.
It does not treat strings such as `CHECK` as missing automatically. Numeric
predictions can be fractional, so counts may need a separate rounding rule.

This step can be slow on wide datasets. For later predictive modelling, split
the data first and fit imputation using training data only. This cleaning
function fits on all rows passed to it; it is not a reusable train/test imputer.

## Feature Selection for Recorded Death

Run all configured selection methods, each selecting **at most 20
original attributes**:

```bash
python src/select_features.py
```

Run the complete workflow (clean the data and save the CSV, then run feature
selection):

```bash
python src/run_pipeline.py
```

Both commands work from the project folder. Module execution, such as
`python -m src.select_features`, is also supported. The standalone selector
accepts `--input`, `--output-root`, and `--seed`. Its input must be the raw CSV,
not the CSV already imputed on all patients.

### How the comparison works

- The target is `zgon`, with **1 assumed to mean death and 0 no recorded death**.
  Confirm this coding against the source documentation. Missing target labels
  are excluded, never imputed.
- **ROC AUC is the primary comparison metric.** Order methods by mean validation
  ROC AUC and report its standard deviation across folds. Other metrics are
  supporting results; final test scores are for reporting, not model selection.
- Keep 20% of patients for the final test. Use the other 80% for training and
  five-fold stratified validation. All methods use the same splits.
- Fit pruning, imputation, encoding, scaling and selection using training rows
  only in each fold. The full-workflow command creates the usual cleaned CSV,
  but selection starts separately from raw data to avoid full-data imputation.
- For these baseline models, use training-fitted median imputation for numbers
  and most-frequent imputation for categories. The existing MissForest cleaning
  function cannot reuse fitted models on unseen rows, so it is not used here.
- Logistic regression ranks by absolute coefficients after numeric scaling.
  The decision tree ranks by impurity reduction. Scores for one-hot columns
  are summed under their original attribute name; each output list has at most 20
  original names, not 20 dummy columns. These scores have different scales,
  and summed category scores can favor attributes with more categories.
- Rank on training data, select at most 20 names, and refit the model on those names.
  Repeat this entire process for every validation fold. Final names are learned
  from the full training portion; the final test labels are used only to score.
- Keep at most 20 original attributes with positive importance. If fewer
  qualify, retain the smaller set; do not pad with zero-score columns. If none
  qualify, score a constant training-prevalence predictor instead.


Known identifiers, `tryb`, source dates and death/follow-up durations are excluded.
In particular, `Time of observation` and `days_implantation_to_end` use outcome
timing and must not be used to predict the outcome. Numeric category codes are
currently treated as numbers; their meanings still need a data-dictionary review.

### Boruta

BorutaPy uses random forests and shuffled shadow features to label features as
confirmed, tentative or rejected. It runs independently on each training fold,
using 128 trees, a maximum of 50 iterations and random seed 42 by default.
Its settings are in `src/feature_selection/model_based/boruta.py`.

To cap the comparison at 20 original attributes, order by best
encoded Boruta rank, then summed median importance, then name. An original
attribute is confirmed if any encoded category is confirmed; otherwise it is
tentative if any category is tentative. This grouping is a reporting convention.
Inspect `boruta_status` and `boruta_rank` in `feature_rankings.csv`: selected
attributes added to reach 20 are not necessarily confirmed. If more than 20
are confirmed, the comparison retains 20 and the full ranking still records
the rest.

Boruta is a selector, not a classifier. Its selected set is evaluated with a
random forest; logistic and tree selections use their corresponding classifiers.
ROC AUC therefore compares complete selector/classifier combinations. These
results do not isolate the effect of feature selection alone.

### Saved results

Each run creates a new UTC-named folder under `results/feature_selection/`:

| File | Contents |
| --- | --- |
| `config.json` | Settings, class counts, data hash, model parameters, software versions and Git state |
| `feature_rankings.csv` | Training-set rankings and selected flags, by method |
| `selected_features.json` | The 20 selected original names for each method |
| `feature_overlap.csv` | Pairwise counts of shared selected attributes |
| `fold_selected_features.csv` | Attributes selected in each validation fold |
| `cv_results.csv` | Scores for every fold and method |
| `cv_summary.csv` | Mean and standard deviation of validation metrics |
| `test_results.csv` | Final held-out scores and aggregate confusion counts |

Generated run folders are ignored by Git. They contain aggregate results and
feature names, not patient records. Open
`notebooks/feature_selection_comparison.ipynb` to compare the latest run,
selected names, overlap and selection frequency across folds.

### Interpretation

This is an exploratory study of **associations with recorded death**, not a
method for establishing the cause of death. Follow-up duration varies, so the
outcome is not death within a fixed time period. Measurement timing and category
codes are incompletely documented; more outcome proxies may need to be excluded
when the data dictionary is available. Do not repeatedly use final test scores
to tune the models or choose attributes.

## Team Git Workflow

To keep our codebase stable and organized, we follow an Issue-Driven workflow.

1. **Create an Issue First:** Before writing code, open an issue. **Ensure the issue has a clear finish line** (e.g., "Impute missing age values" instead of "Look into missing data"). If an issue is too vague, break it down.
2. **Branch per Issue:** Create a dedicated feature branch for your issue branching directly off `main` (e.g., `feature/12-impute-age`).
3. **Merge via Pull Request:** Never push directly to `main`. When your work is done, open a Pull Request (PR) and have at least one team member review and approve it before merging.

Keep each issue focused on one task. Include the cleaning function and its
call in `clean_data.py` in the same PR. If two people need to edit the same file,
agree on who changes what. Before merging, update your branch from `main` and
run the pipeline again. If your work needs another PR, wait for that PR to merge first.

## Team Workflow: Adding Cleaning Steps

`src/clean_data.py` runs the pipeline: it loads the data, calls the cleaning
functions in order, and saves the result. Put cleaning logic in
`src/cleaning_steps/`.

1. **Create an issue and a branch from `main`.** Follow the Team Git Workflow above.
2. **Choose a file for your task.** The current files are:
   * `text_normalization.py`: Clean column names and text.
   * `missing_values.py`: Fill missing numeric and categorical values with iterative random forests (MissForest).
   * `date_formatting.py`: Fix dates and calculate observation time.

   Keep similar tasks together. You can add files such as `type_casting.py`
   for changing data types or `imputation.py` for filling missing values.
   These are examples, not files you must create now. You do not need a
   separate file for every function.

3. **Write a function that takes a DataFrame and returns a cleaned copy.**
   Keep loading and saving in `clean_data.py`. Explain which columns your
   function needs. Use this pattern:

   ```python
   def clean_something(df):
       df = df.copy()
       # Apply your cleaning rules here.
       return df
   ```

4. **Add the function to `src/clean_data.py`.** Add its import in both branches
   of the existing `if __package__` block, following the other imports.
   Then add `df = clean_something(df)` inside `clean_data(df)`.
   Put it after any steps it depends on and before the final
   `df.convert_dtypes()`. Keep the other steps in place.
5. **Run the pipeline from the project folder:**

   ```bash
   python src/clean_data.py
   ```

   Open `data/processed/cardiac_patient_data_clean.csv` and check the columns
   you changed. Check missing values and unusual inputs too. If you changed
   imports, also check that the notebook can still import the pipeline.
6. **Open a PR linked to your issue.** Explain what changed and how you checked
   it. Ask a teammate to review it before merging.

## Unified Feature-Selection Evaluation

`notebooks/test_feature_selection_techniques.ipynb` is restored unchanged from
its original ANOVA/MI/RF/RFE version. All validated method comparisons now live
in `notebooks/feature_selection_comparison.ipynb`.

Run `python src/select_features.py`, then open the comparison notebook. It
includes logistic regression, decision tree, ANOVA, mutual information,
random-forest importance, RFE, Boruta, Lasso, Elastic Net and XGBoost. Every
method repeats training-only preprocessing and selection on the same five
folds within an 80% training split; the remaining 20% is held out. ROC AUC is
the primary metric. Select at most 20 original attributes with positive
importance, never zero-score padding. Boruta statuses remain separate from
the capped set. ANOVA, MI and RFE use logistic regression for evaluation;
other methods use their corresponding classifier, with random forest for
Boruta. This compares selector/classifier combinations, not selectors alone.

Method code is grouped under `baselines/`, `statistics/`, and `model_based/`.
RFE removes 10% of encoded inputs per iteration, and original-column rank is
its best encoded rank. All methods use initial fixed settings, not tuned
settings. Earlier standalone sparse-logistic scores used different validation
splits and should not be compared directly to this unified run.


The comparison notebook shows only the top five chosen attributes per method.
`top20_attributes_by_method.csv` saves the complete capped selections together
(rows: ranks 1–20; columns: methods). `attribute_selection_frequency.csv` counts
how many methods chose each attribute across their complete final selections.
Cross-validation frequency is saved separately as `fold_selection_frequency.csv`.


Final attribute exports include only methods with **mean cross-validation ROC
AUC >= 0.70**. The cutoff is `MIN_ROC_AUC` in `reporting.py`; a score exactly
0.70 qualifies. All methods remain visible in performance tables and full
rankings. `method_eligibility.csv` records the decision. The combined top-20 CSV,
`selected_features.json`, overlap and agreement counts use eligible methods only.
`all_method_selected_features.json` preserves the unfiltered selections for audit.
Held-out test ROC AUC is never used to choose eligible methods.


### Final consensus selection

The eligible methods vote to produce one final list of 20 original attributes.
Each method gives one vote per chosen attribute. Sort by votes, then mean rank
points across all eligible methods: `(21 - rank) / 20`, with zero for absence.
Remaining ties are alphabetical. `final_selected_attributes.csv` contains the
final rank, feature, votes, mean rank points and selecting method names;
`consensus_attribute_ranking.csv` retains all candidates. If fewer than 20
candidates exist, save the smaller set rather than padding it. The comparison
notebook displays the final list. This is a descriptive consensus, without an
independent consensus ROC AUC; qualifying methods and voting would need to be
repeated within training splits for that evaluation.
